# Website SEO Improvement Plan

Timestamp: 2026-07-19T21:49:55-05:00

Status: Planning only. This note does not implement any SEO changes.

## Goal and ranking method

Increase qualified organic discovery of the public Ancient Egypt and the Bible Q&A archive while preserving transcript-grounded accuracy and avoiding mass-produced, low-value pages.

The work items below are independently shippable and are ranked from easiest/fastest to hardest/slowest for one maintainer familiar with the repository. Effort is an estimate, not a deadline. The ranking is by implementation effort, not expected SEO impact. Interlocks and shared-file conflicts are called out explicitly.

## Current repository baseline

- The Hugo data currently represents 283 episodes, 281 curated question pages, and 13,689 question rows.
- The deployed base URL is `https://r-jack-ray.github.io/ancient-egypt-and-the-bible/`, a GitHub Pages project subdirectory.
- `site/layouts/_default/baseof.html` emits a viewport tag, a title, and a favicon, but no meta description, canonical link, Open Graph metadata, robots directive, or structured data.
- Generated question-page front matter already has a `description`, but the base layout does not publish it as a meta description. For numbered streams, that description is usually only an episode label such as `Live Stream #270: Dead or Ankh`, not a useful summary of page content.
- Hugo should generate a sitemap by default, but the current validation script does not inspect the rendered sitemap or assert that it contains only canonical, indexable URLs with the deployment subpath.
- `/search/` is a client-rendered internal search interface with little static content and query-parameter variants. It currently has the same indexability treatment as content pages.
- The archive has episode navigation and index pages, but no topic hubs, visible breadcrumbs, stable per-question permalinks, About/methodology page, or explicit authorship/editorial provenance.
- A public `robots.txt` under the project subdirectory would not control crawling for `r-jack-ray.github.io`; robots rules are read from the host root. Google also does not support a distinct site name for a subdirectory-level site. A custom domain would remove both limitations, but is not required for the other work.
- The current static Hugo compatibility checks and search-alias checks pass. A full local Hugo render could not be completed during this planning pass because Hugo is not installed locally; the deployment workflow installs Hugo and performs the real build.

## Important interlocks and exclusions

1. **Shared head-template work:** Ranks 2-5 and 12 are logically independent but all touch `site/layouts/_default/baseof.html`. To avoid branch conflicts, either implement them sequentially or first extract a small SEO head partial and assign one owner to that file.
2. **Deployment URL:** Canonicals, social URLs, and sitemap tests must derive from Hugo's configured/deployment `baseURL`. Never hard-code localhost or assume the GitHub project path will remain permanent.
3. **Custom-domain decision:** Rank 14 does not block quick wins. If it is likely, make metadata URL-aware now and delay large off-site promotion until the final domain is chosen.
4. **Content expansion quality gate:** Topic hubs and question pages must add navigation, context, synthesis, or unique usefulness. Republishing the same answer under many URLs creates duplication and may look like search-engine-first mass production.
5. **Structured-data eligibility:** The current episode pages contain many publisher-authored questions, not one community question with user-submitted answers. `QAPage` is therefore invalid, and FAQ rich results are generally restricted to authoritative government and health sites. Use breadcrumbs now; use video markup only after a true watch-page implementation.
6. **Generated content ownership:** Continue editing `docs/questions/*.md` and the generator, not ignored `site/content/questions/*.md` mirrors. Any SEO metadata that needs editorial control should be stored in an authoritative source or a dedicated tracked data file.
7. **Accurate freshness only:** Do not set `lastmod`, publication dates, or visible "updated" dates to the current build time. Dates should reflect a substantive source or editorial change.

## Ongoing maintenance for new and revised episodes

Apply ranks 2-8 to every new episode through the existing source-to-site workflow so the initial SEO work does not go stale:

1. Add or revise only the authoritative `docs/questions/*.md` page. The generator automatically gives every generated episode mirror the shared title, H1, canonical URL, sitemap treatment, and a unique description built from representative curated questions.
2. Review the generated title and description for accuracy, readability, and representative topics. If question sampling produces a weak description, add one transcript-grounded `<!-- seo-description: ... -->` override near the top of the authoritative page; never edit the generated mirror.
3. Run `scripts/Test-HugoSite.ps1 -SkipHugo` before committing. It regenerates the mirrors and rejects missing, malformed, or duplicate descriptions, including future episodes.
4. Keep the deployment SEO checks in CI. They must continue verifying unique titles/descriptions, one matching H1, production-base-path canonicals, and exact sitemap inclusion while excluding `noindex` pages such as search.
5. After deployment, spot-check the new episode's rendered metadata and sitemap URL. Record only real editorial dates; do not introduce build-time `lastmod` values.

## Suggested first delivery batch

The best initial impact-to-effort batch is ranks 1-8. It establishes measurement, removes the weakest index target, publishes correct titles/descriptions/canonicals, verifies the sitemap, improves generated descriptions, and adds regression protection. Ranks 9-13 can then improve trust, internal navigation, sharing, and page experience without waiting for a taxonomy or custom-domain decision.

After each deployment, record the release date and compare Search Console data over at least 28-day windows. Primary measures should be indexed canonical pages, non-branded impressions and clicks, CTR by landing page/query, query coverage, crawl/indexing errors, and Core Web Vitals. Do not judge content-architecture changes after only a few days.
